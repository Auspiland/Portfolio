스캔본과 텍스트가 섞인 공공기관 업무계획서 PDF를 OCR부터 구조화, 검색 색인까지 잇고 기존 운영 포털에 붙였습니다.

43 / 43전체 문서 OCR · 색인 완료
결론
구조화 검사를 통과하지 못한 문서는 페이지 단위로 처리했습니다. 추출한 내용은 원문과 대조해 확인했습니다.
확인
전체 문서를 전수 구조 검증을 거쳐 색인했고, 검색 집계를 담당자가 원한 문서 단위로 맞춰 새 주소 없이 기존 운영 포털에 병합했습니다.
적용 범위
임베딩을 더한 하이브리드 검색까지 만들어 검증했지만, 운영 반영본은 고객 결정에 따라 BM25만 남겼습니다. 원문 대조 채점은 세부계획 문서에만 적용했습니다. 스크립트 작성과 서버 실행은 AI에 맡기고, OCR 선택·검색 단위·배포 방식은 제가 정했습니다.
OpenSearch · BM25OCRHDFS
상황과 한 일
상황
서버의 기존 OCR·검색 시스템은 줄 구조와 위치를 버리고 페이지 평문만 돌려줘, 목차·과제 단위 검색에 쓸 수 없었습니다. 담당자가 원한 것은 문서 단위 검색과 원본 PDF 내려받기였습니다.
한 일
기존 OCR의 코드를 살펴보고 다른 후보를 호출해 응답을 비교한 뒤, 사용할 OCR을 골랐습니다. 큰 스캔 문서는 나눠 처리했고, 깨진 텍스트 레이어를 읽을 수 있다고 오판하던 문서는 이미지 OCR로 돌렸습니다. 목차 → 섹션 → 과제 3단계로 구조화하되, 순서·제목 적중·과제 수 검사를 통과하지 못하면 페이지 단위로 후퇴하게 했습니다. 원문 대조 채점에서 옛 문서의 글머리 기호가 영문자로 읽혀 일정 항목이 비던 것을 찾아 인식 단계에서 고쳤습니다.
이후
내려받기가 간헐적으로 실패하자 원인이 HDFS 네임노드 HA의 대기 노드로 요청이 가는 것임을 추적해, 다른 시스템이 함께 쓰는 설정은 두고 클라이언트만 고쳤습니다. 최종 사용자 화면은 다른 팀이 담당했습니다.
SQL · Index

검색 인덱스의 참여자 정보 보완

연구 성과 검색 인덱스에서 참여자 사번이 대량으로 비어 있었습니다. 동명이인 위험이 있는 이름 매칭 대신, 문서 안의 순번 필드로 채웠습니다.

결론
과제·성과 번호와 참여 순번, 네 개 키로 조인해 이름 매칭 없이 사번을 보완했습니다.
확인
병합 실행은 별도 감시 에이전트로 진행과 오류를 지켜보며 실패 없이 끝냈습니다. 남은 누락은 원인별로 나누고, 운영 DB를 확보했을 때 쓸 복구 키까지 문서로 남겼습니다.
적용 범위
개발 서버의 데이터로 한 작업이고, 운영 DB를 확보하기 전까지 남은 누락은 보류 상태입니다. 조회와 실행은 AI가 했고, 범위와 진행 여부는 제가 정했습니다.
SQL · PostgreSQLOpenSearchDelta Lake · Parquet
상황과 한 일
상황
이전 시도들은 이름 매칭과 오래된 개발 DB 조인으로 서로 다른 결과를 남긴 채 흩어져 있었습니다. 최신 데이터가 있는 운영 DB에는 접근할 수 없었습니다.
한 일
전체 재처리와 필드만 추가하는 방식의 소요를 비교해 제시하고, 필드 추가로 범위를 정했습니다. 인덱스 문서 수가 실제보다 몇 배 크게 보이던 것은 첨부파일이 중첩 필드로 합산된 값임을 문서 단위 실측으로 밝혀 작업 대상을 다시 정했습니다. 개발 DB는 SQL로 데이터가 멈춘 시점을 확인해, DB로 채울 수 있는 양이 매우 적다는 한계를 먼저 보고했습니다. 그 뒤 과제·성과 번호와 참여 순번, 네 개 키로 조인해 사번을 채웠습니다.

스트리밍 스키마 계약

여러 스트리밍 앱이 Kafka로 이어지는 파이프라인에서, 스키마가 어긋나도 저장 직전까지 조용히 흘러갔습니다.

결론
스키마 선언을 필수로 바꾸고, 선언이 빠진 요청은 입력 단계에서 오류로 처리했습니다.
확인
"추측 → 조용한 기본값" 경로가 사라졌고, 새 스트리밍 앱은 계약만 지키면 추가할 수 있게 됐습니다. 리팩터 중 잠복해 있던 미정의 오류도 코드를 정독하며 함께 걷어냈습니다.
적용 범위
AI 보조로 진행한 PoC 맥락입니다. 계층 사이에서 같은 이름이 다른 뜻으로 쓰이는 문제까지는 다루지 못했고, 그 문제는 데이터 설계로 이어졌습니다.
Spark Structured StreamingKafkaDelta Lake

상황
스키마를 토픽명으로 딕셔너리에서 추측하고, 못 찾으면 부분 문자열로 맞추고, 그래도 없으면 조용히 기본 스키마로 진행하던 구조였습니다. 잘못된 스키마는 저장 시점에야 터졌고, 그때는 어디서 어긋났는지 되짚기 어려웠습니다.

Scale · Reprocessing

대용량 재처리 파이프라인

파싱된 문서를 운영 검색 인덱스에 다시 적재하는 파이프라인에서, 전체 데이터를 처리할 때 저장 오류·지연·중복이 발생했습니다.

1만 2천 → 67한 문서의 중복 청크 · 같은 청킹 조건
결론
청크 ID를 결정적 값으로 발급해, 다시 실행해도 같은 항목이 갱신되도록 바꿨습니다.
확인
한 문서에 쌓여 있던 청크 1만 2천여 개가 67개로 정합됐고, 임베딩은 실패 없이 완주했습니다. 품질 검증을 길이 비교에서 해시 전수 대조로 바꾸자, 손상으로 의심하던 건들이 실은 분할할 수 없는 문서의 복제였음이 드러났습니다.
적용 범위
같은 청킹 조건에서의 멱등성입니다. 청커 버전이 바뀌면 전체 재처리는 피할 수 없고, 그 경계를 정하는 일은 데이터 설계로 넘겼습니다. 팀 운영 시스템이며 구현에는 AI를 썼습니다.
OpenSearchPyArrow · ParquetUUIDv5
상황과 한 일
상황
재청킹과 재임베딩을 거쳐 운영 벡터 인덱스에 다시 넣어야 했습니다. 전체 규모에서 저장 오류, 지연, 중복이 한꺼번에 나타났는데 로그상 실행은 성공으로 끝나 있었습니다.
한 일
추측 대신 원인을 단위별로 나눠 측정했습니다. 임베딩 실패 행의 빈 벡터가 고정 크기 스키마를 깨뜨린 것은 가변 스키마와 원자적 쓰기로, 입력 크기와 무관하던 고정 지연은 배치 조정으로 풀었습니다. 인덱스가 부푼 원인을 청크 순서 분포로 추적하니 재실행 누적이었고, 청크 식별자를 결정적 값으로 발급해 재실행해도 같은 id로 갱신되게 했습니다.

재현율 1위가 최악의 표였다

PDF를 문서 AI가 쓸 형태로 바꾸는 후보들을 비교했습니다. 문자 재현율이 가장 높은 후보를 고르면 끝나는 줄 알았습니다.

0.999 → 0.25문자 재현율 · 평가 구간을 고친 뒤 재측정
결론
병합셀의 복제와 잘못 선택한 평가 구간 때문에 문자 재현율이 높게 나왔습니다. 실제 표 구간으로 다시 평가했습니다.
확인
표 구조와 페이지·위치 정보를 함께 남기는 후보를 채택했습니다. 처음 기대한 표 보존만 보면 HTML 경로도 괜찮았지만, 답변 근거를 원문으로 되짚어야 하는 시스템에는 부족했습니다.
적용 범위
단기 PoC입니다. 실행은 AI가 했고 실험 설계와 판정은 제가 했습니다. 같은 태도를 처음부터 설계에 넣은 것이 설비 상태 트윈입니다.
통제 실험문서 파싱재현율 · 구조 보존
상황과 한 일
상황
HTML을 거치면 표 손실이 적을 것이라는 제 가설이 있었습니다. 비교 경로와 반드시 남겨야 할 정보(표 구조, 페이지·위치 출처)를 먼저 정하고, 실험 구현과 실행은 AI에 맡겼습니다.
한 일
첫 결과에서 재현율이 가장 높던 후보는 병합셀 내용을 열마다 복제해 문자량을 부풀리고 있었고, 표 구조는 하나도 보존하지 못했습니다. 두 파서가 같은 구간의 표 개수를 다르게 세는 불일치를 오류 신호로 보고 끝까지 재검증하자, 평가 구간 자체가 표가 아니라 점선 목차였습니다. 실제 표 구간만 다시 재면 그 후보는 꼴찌였습니다.

구형 GPU에서 문서 인식 모델 실행

최신 문서 인식 모델을 폐쇄망의 구형 GPU에 올려야 했습니다. 추론 프레임워크는 그 GPU 세대의 지원을 이미 끝냈고, 하나뿐인 노드는 다른 팀 배포가 차지하고 있었습니다.

결론
기존 호출부를 유지할 수 있도록 같은 요청 형식을 받는 어댑터 서버를 만들었습니다. GPU 자원을 회수하기 전에는 복구 명령을 남겼습니다.
확인
모델은 품질 평가용으로 배포돼 결과를 낼 수 있었고, 회수한 자원은 언제든 되돌릴 수 있는 상태로 남았습니다.
적용 범위
배치 처리 없이 직렬로 도는 품질 평가용 배포입니다. 운영 처리량으로 일반화하지 않습니다.

상황
